# Spec Type 与 Contract

## Type 是可配置分类

初始化时，用户先在任意已有路径准备配置文件；不能假定目标项目的 `spec/` 目录已经存在。例如可在项目根目录准备 `init.yaml`：

```yaml
specTypes:
  capability:
    label: 能力
    description: 面向用户或外部系统的可观察行为
  component:
    label: 组件
    description: 模块职责、边界、接口与依赖
  rule:
    label: 规则
    description: 跨能力或组件适用的稳定约束

kinds:
  feat:
    label: 功能
    description: 新增或扩展正式能力、组件或规则
  bugfix:
    label: 修复
    description: 修复实现或正式 spec 的错误
```

`init.yaml` 必须同时声明非空的 `specTypes` 与 `kinds`，与 `spec/config.yaml` 结构完全相同。CLI 随发行提供一份含默认 `specTypes` 与 `kinds` 的初始化文件，用户可直接复制作为起点。

执行以下命令后，CLI 校验输入并创建 `<target>/spec/config.yaml` 作为项目的持久配置：

```text
specify init . --config init.yaml
```

也就是说：`init.yaml` 是初始化输入，`spec/config.yaml` 是初始化成功后的项目配置输出。CLI 应拒绝把目标 `spec/config.yaml` 当作首次初始化的必需输入。

CLI 只允许创建已声明 type 的正式 spec：

```text
specify create capability user-auth
specify create component auth-service
```

所有正式 spec 位于 `specs/<type>/<id>/spec.md`。type 不从 Markdown 内容猜测，也不由 change 的 kind 决定。

## Contract 是统一的变更单位

`capability` 不再是 OpenSpec 意义上的唯一 spec 单位。它只是一个 type；每个 type 的 spec 都由 Contract 组成。

Contract 同时有显式 ID 和可读标题。ID 是所属 spec 内唯一的 kebab-case 标识；标题可以使用中文、空格和业务术语。修改标题或正文都不改变 ID。

`type` 从项目配置选择；`spec-id` 由作者在 `specify create <type> <spec-id>` 或 change 的 `--affect` 参数中指定；新增 Contract 时，作者或 Agent 为它选一个简短的 `contract-id`（如 `password-login`），放在标题开头的 `[]` 内。CLI 校验格式和同一 spec 内的唯一性，不从中文标题、正文或 hash 自动推导 ID。完整引用只是把这三段拼接起来，不另行生成。

跨 spec 引用 Contract 时，使用三级规范引用：

```text
<type>:<spec-id>:<contract-id>
```

例如：

```text
capability:user-auth:password-login
component:auth-service:credential-validation
component:sms-gateway:message-delivery
```

`--affect` 的第三个字段是 **spec 级**操作（`create`/`modify`/`remove`），不是 Contract ID。Contract 引用中的第三段是显式 ID，只在正式 spec、delta 与定位输出中使用。

这里采用 `<spec-id>` 而不采用 `instance`，避免和运行时对象实例混淆；它就是该 type 下的具体 spec 目录名。Contract ID 只要求在同一 spec 内唯一，不要求跨 spec 唯一；三级引用保证全局唯一。ID 创建后保持不变，即使标题通过 `RENAMED` 改写，也继续使用原 ID。

标题仍需在同一 spec 内保持唯一，比较时采用 `NFKC(trim(collapse-whitespace(title)))`；这只用于发现重复标题和核对 delta 中的旧标题，不再生成身份 hash。正文版本 hash 另见 [07-contract-version-check.md](07-contract-version-check.md)，它只用于冲突检测。

正式 spec 的通用骨架：

```markdown
# contract

## [credential-validation] 凭据验证的职责

认证服务负责验证凭据并返回认证结果。

## [memory-responsibilities] bytes/int/deref 的职责拆分

明确 bytes、int 和 deref 各自的职责与边界。

## [string-decoder-reuse] 字符串命令复用 MemoryInspector decoder

字符串命令通过 MemoryInspector decoder 复用既有解码逻辑。
```

正式 spec 只保存当前生效的 Contract；change 的 `change.md` 随 change 归档。`# contract` 下每个 `## [<contract-id>] <title>` 区块都是一个可被 delta 更新的 Contract。方括号明确标出 ID 的边界，标题本身仍可使用冒号。每个 type 可以在 Contract 正文中表达不同内容，例如 capability 的行为、component 的边界与依赖、rule 的适用范围；但更新单位一致。

## V1 不提供 Templates

V1 不实现 type template，也不在 `config.yaml` 中配置 `template` 字段。`specify create <type> <spec-id>` 只创建固定的最小骨架：

```markdown
# contract

## [contract-id] Contract title

<!-- 描述这条 Contract 的责任与行为。 -->
```

用户或 Agent 再补充稳定 ID、自然语言标题和正文。占位注释不算有效正文，补齐前 `validate --specs` 不通过。未来若引入 templates，应作为独立 feature：它只能协助创建文件，不能改变 `# contract`、显式 ID 规则和 delta 协议。

## 旧格式迁移

启用显式 ID 校验前，已有正式 spec 的每个 `## <title>` 都要补上稳定 ID；仍在进行的 delta 也要使用同一 ID。中文标题不自动转写为 ID，以免生成难以理解或不稳定的名字。已归档 change 保持原样，作为当时协议下的历史记录。

## 统一模型带来的结果

```text
specs/capability/user-auth/spec.md
  └── [password-login] 密码登录

specs/component/auth-service/spec.md
  └── [credential-validation] 凭据验证的职责
```

两者的 type 不同，但 delta 协议、索引方式和定位规则一致。

## `spec-index.md`

CLI 从正式 spec 的 type 与 spec-id 生成并覆盖 `spec-index.md`。索引只扫描 `specs/<type>/<spec-id>/spec.md`，不收录 change、delta 或 archive。分组标题使用首字母大写的 type key（`## Capability`），具体规则见 [format/spec-index.md.md](format/spec-index.md.md)。

```markdown
<!-- Generated by specify index build. Do not edit. -->

# Spec Index

## Capability

- [`user-auth`](specs/capability/user-auth/spec.md)

## Component

- [`auth-service`](specs/component/auth-service/spec.md)
```
