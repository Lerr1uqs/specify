# Spec Type 与 Contract

## Type 是可配置分类

初始化时，用户先在任意已有路径准备配置文件；不能假定目标项目的 `spec/` 目录已经存在。例如可在项目根目录准备 `init.yaml`：

```yaml
specTypes:
  capability:
    label: 能力
    description: 面向用户或外部系统的可观察行为
  component:
    label: 组件
    description: 模块职责、边界、接口与依赖
  rule:
    label: 规则
    description: 跨能力或组件适用的稳定约束
```

执行以下命令后，CLI 校验输入并创建 `<target>/spec/config.yaml` 作为项目的持久配置：

```text
specify init . --config init.yaml
```

也就是说：`init.yaml` 是初始化输入，`spec/config.yaml` 是初始化成功后的项目配置输出。CLI 应拒绝把目标 `spec/config.yaml` 当作首次初始化的必需输入。

CLI 只允许创建已声明 type 的正式 spec：

```text
specify create capability user-auth
specify create component auth-service
```

所有正式 spec 位于 `specs/<type>/<id>/spec.md`。type 不从 Markdown 内容猜测，也不由 change 的 kind 决定。

## Contract 是统一的变更单位

`capability` 不再是 OpenSpec 意义上的唯一 spec 单位。它只是一个 type；每个 type 的 spec 都由 Contract 组成。

Contract 的标题是正常 Markdown 标题，可以使用中文、空格和业务术语；它不再要求 kebab-case ID。CLI 只对 Contract 标题计算确定性的 hash，正文内容绝不参与计算。

跨 spec 引用 Contract 时，使用三级规范引用：

```text
<type>:<spec-id>:<contract-hash>
```

例如：

```text
capability:user-auth:5db1c9f8
component:auth-service:9aa30d42
component:sms-gateway:9aa30d42
```

这里采用 `<spec-id>` 而不采用 `instance`，避免和运行时对象实例混淆；它就是该 type 下的具体 spec 目录名。hash 的输入只能是规范化标题：`NFKC(trim(collapse-whitespace(title)))` 的 UTF-8 SHA-256 值（显示时可使用不冲突的前缀）。正文绝不参与 hash，因此修改 Contract 内容不会改变引用。标题是 identity 的来源：修改标题必须走 `RENAMED` 操作，并计算出新的 title hash。

hash 是每次读取 Markdown 时即时派生的值，不写入本地数据库、缓存、sidecar 或 metadata。计算成本可以忽略，文档标题是唯一事实来源；这样不需要维护“已存 hash”与文档之间的同步。

正式 spec 的通用骨架：

```markdown
# proposal

简要说明当前 spec 的上下文、目的与动机。

# contract

## 凭据验证的职责

认证服务负责验证凭据并返回认证结果。

## bytes/int/deref 的职责拆分

明确 bytes、int 和 deref 各自的职责与边界。

## 字符串命令复用 MemoryInspector decoder

字符串命令通过 MemoryInspector decoder 复用既有解码逻辑。
```

`# proposal` 是可被索引的简要上下文、目的与动机；`# contract` 下的每一个 `##` 区块就是一个可被 delta 更新的 Contract。其引用 hash 由 `##` 标题本身计算，无需在 Markdown 中另存 marker。每个 type 可以在 Contract 正文中表达不同内容，例如 capability 的行为、component 的边界与依赖、rule 的适用范围；但更新单位一致。

## V1 不提供 Templates

V1 不实现 type template，也不在 `config.yaml` 中配置 `template` 字段。`specify create <type> <spec-id>` 只创建固定的最小骨架：

```markdown
# proposal

<!-- 简要叙述当前 spec 的上下文、目的和动机。 -->

# contract
```

用户或 Agent 再补充自然语言 Contract 标题和正文。未来若引入 templates，应作为独立 feature：它只能协助创建文件，不能改变 `# proposal`、`# contract`、标题 hash 规则和 delta 协议。

## 统一模型带来的结果

```text
specs/capability/user-auth/spec.md
  └── 5db1c9f8: 密码登录

specs/component/auth-service/spec.md
  └── 9aa30d42: 凭据验证的职责
```

两者的 type 不同，但 delta 协议、索引方式和定位规则一致。

## `spec-index.md`

CLI 从每份正式 spec 的 `# proposal` 中提取简介，生成并覆盖 `spec-index.md`。索引只扫描 `specs/<type>/**/spec.md`，不收录 change、delta 或 archive。

```markdown
<!-- Generated by specify index build. Do not edit. -->

# Spec Index

## Capability

- [`user-auth`](specs/capability/user-auth/spec.md) — 提供注册、登录和会话管理。

## Component

- [`auth-service`](specs/component/auth-service/spec.md) — 负责认证决策与会话签发。
```
